# v0.2 final review and local delivery

Router Step 6 consumes the current successful preview and latest critic diagnosis `final_review_required`. Inspect the PNG, actual setup BLEND, retained geometry/surface/reference provenance and the immutable snapshot before asking the user for a final decision:

```text
python -m runtime.cli final-review-context PROJECT
python -m runtime.cli final-review-v02 PROJECT --decision approved --expected-version N
python -m runtime.cli deliver-v02 PROJECT --expected-version N_PLUS_1
```

`N` is the current Manifest version reported by context. These commands require explicit authorized mode `full_pipeline`, `stage2_only` or `repair`. The final decision command is a user approval boundary; an agent diagnosis, valid files, a test fixture, or `auto_approve` cannot substitute for the user's decision. The existing `review-context` state boundary stays unchanged.

Completion evidence is captured during successful preview completion, while the operation packet's Manifest guard is still valid. It requires the current pass setup BLEND, setup receipt, blockout and render worker receipt. Geometry fingerprints must agree before setup, after setup and after rendering. The record binds current Stage 0/scene plans and geometry results, raw project file hashes, selected style resources and worker source bytes. Each new completion transaction seals repository dependency bytes under `stage2/completion-resources/SHA256/REPOSITORY_RELATIVE_PATH` and records the original repository-relative mapping. A later preview can use an upgraded worker or resource while its history verifies the sealed old bytes; the current preview still verifies live repository dependencies before final approval and delivery. Archive conflicts, missing or changed copies reject. Failed completion writes roll back newly staged metadata and dependency copies. Existing evidence without archives retains its original checks and is never backfilled. Old previews without current setup evidence remain inspectable under their original contracts but cannot be approved for final delivery; run a new authorized preview. Evidence is never backfilled.

Final context rechecks the captured bytes and current semantic documents without reusing stale execution-packet guards. User approval writes an immutable final snapshot and hashes all ten current documents plus the snapshot. Rejection uses `--decision rejected`, preserves its snapshot and user decision, and returns `visual_revision`. Supply one new concrete `revision_required` critic on that rejected render using `visual-review-submit`, then the existing bounded `revision-apply` flow. Prior critiques and preview attempt limits remain intact.

Delivery stages only explicitly enumerated formal project files and their history, actual completed preview PNG/setup BLEND/blockout, geometry and original surface files, references, selected repository style/worker resources, prior review evidence, `provenance.json`, and `approved-manifest.json`. It preserves project hierarchy under `project/`, including versioned dependency archives with their repository-relative suffixes. Older completion evidence may retain a separate `repository/` hierarchy; its bytes and hashes remain unchanged. It excludes environment/configuration files, unrelated proposals and whole-project copying. Inventory lists raw SHA256 hashes, excludes itself to avoid a self-reference, and its own raw hash determines `delivery/HASH` and is bound by the official Manifest delivery record.

The manager checks anchors again under its writer lock before publishing the immutable package and changing state to `delivered`. A failed copy or conflicting unregistered package leaves the Manifest and prior packages intact. Repeated delivery requires the current expected version and revalidates the registered package; missing, corrupt or extra files reject. No new final render, GLB export or web publication is claimed. Historical MCP packets are host-bound execution evidence: regenerate them on a new machine before execution.

Engineering tests use explicitly labeled worker/setup doubles and simulated user decisions in temporary projects. The actual mixed-source representative production acceptance remains pending remote HY3D evidence and real user decisions; `projects/industrial_station_v02` remains unapproved `plan_only`.
