# Internal visual task adapters

The Skill owns the complete visual task. Main normally selects execution automatically and remains responsible for image inspection, acceptance and the next production step. Configuration belongs in the host environment or ignored local files, not shared project templates.

`VISUAL_EXECUTION_MODE` is `auto` (default), `main`, or `external`. `VISUAL_EXECUTOR_HOME` locates an optional implementation; `VISUAL_EXECUTOR_PYTHON` locates its isolated Python. `VISUAL_KNOWLEDGE_HOME` optionally points to canonical knowledge. `RENDER_DIRECTOR_HOME` remains a legacy discovery alias. A task preparation specification may override these with `execution_config`: `mode`, `home`, `python`, `knowledge_home`. No credentials belong in this configuration.

Discovery checks all ten public schemas and the real `runtime/load_task.py`, `runtime/publish_result.py`, `SKILL.md` files, plus Python dependencies. Missing or incompatible optional resources select main. Explicit `external` requires a working implementation and reports its actual gap. Selection never catches malformed task inputs, conflicting constraints or stale production baselines.

The file-task adapter supports the current render-director request protocol. `visual-task-start` returns the selected Agent entry and real load/publish commands in `selection.invocation`. The calling Agent reads that entry, executes its load command on the task directory, reads the selected operation instructions, views all declared images and authors the decision. Publish using that implementation's declared stdin format and original input digests. Then collect the declared result with `visual-task-collect`, supplying explicit execution choices for direction tasks. This is serial Agent execution, not a network service or autonomous worker. Helper success alone does not prove visual judgment or production approval.

Main uses the three local visual task prompts and `visual-task-submit` with the same public result schemas. Task records retain the selected executor, actual resource hashes, attempts, accepted result and explicit execution interpretation. See [tracking](task-tracking.md) for recovery. After a confirmed ended optional attempt, auto mode may transfer the same frozen task to main; an explicit external choice does not silently transfer.

Knowledge selection is an Agent decision. Choose a specific question and canonical item IDs, then pass `knowledge.item_ids` during preparation. The resolver reads only those canonical items (and pack declarations), filters operation, renderer and scene applicability and serializes bounded content without editing the source. It retains item/pack versions, content hashes, non-applicability and evidence limitations. `renderer_version` and `applicability_notes` may record the Agent's additional applicability reasoning. No knowledge root or no applicable items omits this input. In particular, create/review-only items never enter refine_direction. Style priors, optional knowledge and observations remain separate inputs.

Legacy RenderContext / RenderDirection / RenderReview projects use the [compatibility guide](render-director.md). They are not converted by editing old direction files or declaring an incompatible helper ready.
